# 数据库范式（1NF / 2NF / 3NF / BCNF）

> 范式是**判断表设计质量的规则**：它描述"一张表的信息该如何组织"，用来**验证**设计是否有冗余和异常，而不是用来**指导**如何从需求建表。怎么从需求做宏观设计，见 [数据库设计：从需求到表结构](./database-design.md)。本文专讲范式本身。

---

## 第一部分：先说三个必懂的概念

要理解 2NF、3NF，必须先分清三个概念：**候选键、主属性、非主属性**。它们是对"一张表的每个字段"做的分类。

### 候选键

**能唯一确定一行的【最小】属性组合。**

- "唯一确定一行"：给这组属性，只对应一行记录
- "最小"：删掉任何一个属性，就不再唯一了

```text
student 表
| id | 姓名 | 邮箱 |
| 1  | 王小华 | wang@edu.com |
| 2  | 陈思远 | chen@edu.com |

id 能唯一确定一行 → 候选键
邮箱也能唯一确定一行 → 也是候选键      ← 候选键可以有多个
```

```text
student_course 表
| student_id | course_id | 学期 | 成绩 |
|     1      |    1      | 2026-秋 | 88.5 |
|     1      |    2      | 2026-秋 | 92.0 |

单独 student_id 不唯一（一个学生选多门课）→ 不是候选键
单独 course_id 也不唯一（一门课多个学生选）→ 不是候选键
但 (student_id, course_id) 合起来唯一      → 候选键（复合候选键）
```

### 主属性 / 非主属性

**主属性 = 出现在某个候选键里的属性；非主属性 = 不在任何候选键里的属性。**

```text
student 表：候选键是 id
  主属性：id
  非主属性：姓名、邮箱

student_course 表：候选键是 (student_id, course_id)
  主属性：student_id、course_id
  非主属性：学期、成绩
```

> 关键点：**"是不是主属性"取决于它是否参与候选键，跟字段名叫什么无关。** 复合候选键里每个属性都是主属性。

### 函数依赖

**`X → Y` 表示「给定 X，Y 唯一确定」**（类比数学函数：同一个 X 只能对应一个 Y）。

```text
id → 姓名        // 知道 id，唯一确定姓名
(student_id, course_id) → 成绩   // 知道谁、选了哪门课，唯一确定成绩
```

> 范式的定义全靠这三个概念。下一节你会看到，每个范式都是在说"**哪些属性之间不能出现什么依赖**"。

## 第二部分：四个范式速览

四个范式**逐级递进**，每一级在上一级基础上多加一条约束，消除一类"表设计缺陷"。

### 1NF：字段必须原子

| 是什么 | 每个字段不可再分，一格只能放一个值 |
|---|---|
| 解决什么问题 | 一个字段塞了"数组/复合值"（如"138…,139…"），导致查不到、没法统计、没法建索引 |

```text
❌ | 老师电话 = "13800000001,13911122233"     ← 一个格两个号
✅ | 电话主号 = 13800000001 | 电话备号 = 13911122233
```

### 2NF：非主属性完全依赖候选键

| 是什么 | 每个非主属性必须【完全】依赖候选键，不能只依赖候选键的【一部分】 |
|---|---|
| 解决什么问题 | 复合候选键的表里，有非主属性只跟候选键的一部分有关（如选课记录里存"课程名"，它只跟课程号有关），导致改一处要改多行、删记录连带删信息 |

```text
❌ 选课记录( student_id, course_id, 课程名, 成绩 )   ← 候选键(student_id,course_id)
                                                      课程名只依赖 course_id → 部分依赖
✅ 选课记录( student_id, course_id, 成绩 )           ← 课程名抽到 course 表
```

### 3NF：非主属性之间不互相依赖

| 是什么 | 非主属性之间不能有函数依赖，不能出现"X → Y → Z"的传递链条 |
|---|---|
| 解决什么问题 | 有非主属性是"别人的属性、借道暂住"（如 course 表里存老师电话），老师换号要改多行、删课连老师信息一起没 |

**看例子**。假设 `course` 表是这么设计的：

```text
course( course_id, 课程名, teacher_id, 老师电话 )
```

**第一步：先分清这张表的候选键、主/非主属性**（这是 3NF 检查的前提）：

```text
候选键 = { course_id }              ← course_id 唯一确定一行
主属性 = course_id
非主属性 = 课程名、teacher_id、老师电话
```

**第二步：在非主属性之间找依赖**：

```text
course_id → teacher_id → 老师电话
  course_id → teacher_id     （合法：主键决定一切）
  teacher_id → 老师电话       （违规：非主属性 → 非主属性）
```

`老师电话` 不直接依赖主键 `course_id`，而是借道 `teacher_id` 间接依赖 → **传递依赖，违反 3NF**。因为它本质是"老师"的属性，不是"课程"的属性。

**修法**：把"老师"抽成独立表，`course` 只留外键指向它。

```text
❌ course( course_id, 课程名, teacher_id, 老师电话 )   ← 传递依赖
✅ teacher( teacher_id, 姓名, 老师电话 )                ← 老师的信息归老师表，主键 teacher_id
   course( course_id, 课程名, teacher_id )             ← 课程只记"谁教的"，外键指向老师
```

### BCNF：决定因素必须是候选键（3NF 的加强版）

| 是什么 | 每个函数依赖 `X → Y` 的左侧 `X` 都必须是【候选键】；连主属性之间的依赖也管 |
|---|---|
| 解决什么问题 | 3NF 只管"非主属性之间的依赖"，BCNF 更进一步：**任何"一个属性决定另一个属性"的依赖，左侧都必须是候选键** |

**看例子**。3NF 解决了"非主属性之间的依赖"，但还有一种情况它管不到——**依赖的左侧不是候选键**。用**医院住院**的例子：

```text
住院记录( 病人, 主治医生, 科室 )
业务事实：
  病人 → 科室         （一个病人固定住在某个科室）
  主治医生 → 科室       （一个医生固定在某科室执业）
```

**第一步：先分清候选键和主/非主属性**（和 3NF 讲解同款走查）：

```text
候选键 = { 病人, 主治医生 }       ← 病人+医生 唯一确定这条住院安排
主属性 = 病人、主治医生
非主属性 = 科室                  ← 科室不参与候选键，是"非主属性"
```

注意：`科室` 虽然业务上很重要，但候选键是 `(病人, 主治医生)`，`科室` 不在其中，所以它是非主属性。

**第二步：列出所有函数依赖，逐条检查左侧是不是候选键**

```text
(病人, 主治医生) → 科室     ← 左侧是候选键 ✓ 合法
病人 → 科室                ← 左侧"病人"不是候选键（它决定不了主治医生）→ 违规
主治医生 → 科室             ← 左侧"主治医生"不是候选键（它决定不了病人）→ 违规
```

**第三步：用 3NF 检查** —— 3NF 只看"非主属性之间有没有依赖"。这里唯一非主属性是 `科室`，它不能自己依赖自己 → **3NF 通过**。

**第四步：用 BCNF 检查** —— BCNF 要求"每个依赖的左侧都是候选键"，而 `病人 → 科室`、`主治医生 → 科室` 的左侧都不是候选键 → **违反 BCNF**。

**为什么违反 BCNF 会出问题？**

`主治医生 → 科室` 这条真实业务规则（医生固定在某科室）没被主键拦住，数据库管不住它。可能出现：

```text
| 病人 | 主治医生 | 科室 |
|  张  |  王医生 | 内科  |
|  张  |  王医生 | 外科  |   ← ？王医生既在内科又在外科？数据打架了
```

同一个病人、同一个医生，本该唯一确定一条住院记录，但 `科室` 可以塞进不同的值——因为"医生属于哪个科室"这条约束没有被数据库表达出来。

**修法**：把"医生→科室"这条约束拆成独立表，让 `主治医生` 成为主键：

```text
❌ 住院记录( 病人, 主治医生, 科室 )     ← 主治医生 → 科室 的左侧不是候选键
✅ doctor_dept( 主治医生, 科室 )        ← 主键 主治医生，"医生在哪个科室"单独管
   住院记录( 病人, 主治医生, ... )      ← 只记"谁负责这个病人"，不再塞科室
```

> BCNF 的直觉：**凡是一个属性"决定了"另一个属性，那它就必须够格当候选键。** 现实中这种"主属性之间纠缠"的依赖不多见，所以 BCNF 遇到再拆即可，不必一开始就追求。

> **记忆**：1NF 拆原子，2NF 去部分，3NF 断传递，BCNF 锁全键。
> **够用就好**：绝大多数业务做到 3NF 就够了，BCNF 少见，按需用。


## 常见误区

| 误区 | 真相 |
|---|---|
| "范式越高越好，全都上 BCNF" | **过度拆分让查询频繁 JOIN，性能反而下降**。满足 3NF 是大多数业务的好选择 |
| "范式是金科玉律" | 范式是**消除异常的设计指导**，不是法律。读多写少、查询目标明确的场景，**故意冗余一个字段省掉 JOIN** 是常见优化 |
| "有主键就一定规范" | 自增主键只是实现细节；**范式看的是函数依赖**，有主键不代表没有部分/传递依赖 |
| "有外键就等于满足范式" | 外键只约束一致性，**范式的核心是消除冗余依赖**，两者维度不同 |
