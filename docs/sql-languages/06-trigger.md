# 触发器（TRIGGER）：操作发生时自动执行的 SQL

> **触发器 = 表上某个操作（INSERT / UPDATE / DELETE）发生时，数据库自动执行的一段 SQL。** 它自己不被调用，是被"事件"触发的。它和视图正好相反：视图是"存一条查询"，触发器是"存一段动作"。
>
> 前置：建议先读 [02 增删改 DML](./02-dml.md)——触发器监听的正是 DML 的增删改，还和事务有关系。

## 1. 触发器是什么：一张"自动动作表"

一句话：**表上某操作发生时，数据库自动执行一段 SQL。** 它由三要素决定：

```text
① 时机（TIMING）：  BEFORE（操作前）还是 AFTER（操作后）
② 事件（EVENT）：   INSERT / UPDATE / DELETE
③ 动作（BODY）：    发生时自动执行的那段 SQL
```

**一个例子**：往学生表插一条记录 → 自动往日志表记一笔"谁在什么时候插了一条"。

```sql
CREATE TRIGGER trg_student_log
AFTER INSERT ON student            -- 时机 + 事件：插入学生之后
FOR EACH ROW                       -- 每次插入一行，都触发
BEGIN
    INSERT INTO student_log(action, created_at)
    VALUES ('INSERT', NOW());
END;
```

> 之后你正常 `INSERT INTO student(...)`，这条日志会被**自动**写上，你不需要、也无法"调用"触发器——它是被插入这个事件带出来的。

## 2. 语法：CREATE TRIGGER 逐段读

```text
CREATE TRIGGER 触发器名
BEFORE | AFTER INSERT | UPDATE | DELETE ON 表名
FOR EACH ROW
BEGIN
    ... 自动执行的 SQL ...
END;
```

**四个部分，各是什么：**

```text
① 触发器名        自己起，见名知意（trg_ 开头是常见约定）
② BEFORE / AFTER  操作前跑，还是操作后跑
③ ON 表名         监听哪张表；FOR EACH ROW = 每影响一行都触发
④ BEGIN ... END   触发器要执行的 SQL 主体
```

**BEFORE 和 AFTER 怎么选？**

```text
BEFORE  操作"还没真正发生"时跑 —— 适合"拦"：校验数据，不合规直接报错，阻止这次操作
AFTER   操作"已经发生"后跑    —— 适合"记"：写日志、同步配套数据，操作已成定局
```

**用 NEW / OLD 访问"那一行的数据"：**

```text
NEW.列名   新值（INSERT / UPDATE 时可用）
OLD.列名   旧值（DELETE / UPDATE 时可用）
```

```sql
-- 删除学生前，先把这个学生的信息留档（防止删了查不到）
CREATE TRIGGER trg_student_backup
BEFORE DELETE ON student
FOR EACH ROW
BEGIN
    INSERT INTO student_deleted(student_id, name, grade, deleted_at)
    VALUES (OLD.student_id, OLD.name, OLD.grade, NOW());
END;
```

## 3. 什么时候该用、什么时候别用

**触发器好不好，取决于你往里面放的是哪种逻辑：**

### ✅ 该用：数据库自己该管的"配套自动化"

```text
① 审计日志：谁在什么时候改了哪条数据 → 自动记一笔
② 自动同步：改主表，自动更新从表（删了老师，课程自动置空）
③ 自动补全：插入时自动填 create_time、updated_at
```

这些的共同点：**不是"业务要的东西"，而是"数据本身的一致性、记录"。** 它们必须跟着主操作发生，不能让写代码的人忘了——触发器"忘不了"，正是它在这里最大的优点。

### ❌ 别用：把"业务逻辑"塞进触发器

```text
❌ "订单金额超过 10000 自动发审批通知"   —— 业务规则
❌ "注册成功自动送优惠券"               —— 业务规则
❌ 任何"要对接外部系统、调接口、发消息"的动作 —— 触发器在数据库里，调不了外部
```

**为什么业务逻辑不该进触发器？** 回到"隐蔽"这个点：

```text
① 看不见：业务逻辑应该写在业务代码里，让开发者看得到、改得了
           藏进触发器，排查问题时根本想不到去翻数据库
② 难调试：触发器没有返回值、不好打日志，出错难查
③ 拖性能：触发器里跑业务逻辑，每次操作都被拖慢
```

> 一句话：**业务逻辑要"看得见"——该在代码里，不该藏在数据库里。** "逻辑太隐蔽"这个缺点，只针对"把业务逻辑藏进触发器"；数据库该管的自动化用触发器，"隐蔽"反而是优点——它保证配套动作不会被代码漏掉。

## 4. 触发器与事务：天然一体，不用你包

触发器会改数据，但**你不需要额外开事务包它**——因为触发器和触发它的那条语句，**天然就在同一个事务里**：

```text
对那条 INSERT / UPDATE / DELETE：
  BEFORE 触发器  ┐
  真正的操作     ├── 全算同一步：要么全成功，要么全回滚
  AFTER 触发器   ┘
```

**三个表现，落实成直觉：**

```text
① 触发器出错 = 整条语句失败
   触发器里报错 → 这条 INSERT 也被回滚，什么都没插进去

② 触发器改别的表，也在同一事务里
   COMMIT 一起提交，ROLLBACK 一起撤销
   不会出现"A 插进去了，B 的日志却没写"

③ AUTOCOMMIT 开着，也是一整件事
   那条 INSERT + 它的触发器作为一个整体立即提交
```

> 所以：**触发器省心（不用包事务），但也更"重"（出错牵连整条语句）**。它常常被当成"最后一道校验"——在触发器里报错，就能把不合规的操作拦下来。

## 5. 常见误区

| 误区 | 真相 |
|---|---|
| "触发器可以手动调用" | **不能调用，只能被事件触发**。写 SQL 时你感知不到它，它是隐形的 |
| "触发器能对接外部系统" | **不能**。触发器只能动当前数据库，调接口、发消息都要靠应用代码 |
| "触发器越多越好" | 触发器是隐形的，**多了难排查、拖性能**。数据库该管的自动化才用 |
| "触发器需要单独开事务" | **不需要**。它和触发它的语句天然同一个事务，COMMIT/ROLLBACK 一起走 |
| "触发器里能写业务逻辑" | **不该写**。业务逻辑该在代码里，藏在数据库里是埋地雷 |

---

**小结**：触发器 = **表上某操作发生时自动执行的 SQL**。它用来做"数据库该管的自动化"（审计、同步、补全），**不该放业务逻辑**；它和触发它的语句**天然同一个事务**，出错会牵连整条语句。

> 和视图对比记：**视图 = 存一条 SELECT（查询时用）；触发器 = 存一段动作（操作时自动跑）。** 它俩一个管"怎么查"，一个管"操作时自动做什么"。
